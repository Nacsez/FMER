stable release. Retain the existing gradual public-beta content and feedback

## Release trigger and assets

Use the readiness gates in [ROADMAP.md](ROADMAP.md), owner signoff and an exact
published stable tag. Keep the numbered build policy. Prepare a short musical
demo, two readable screenshots, feature/shortcut PDFs, source/license links,
release downloads, press pack and [feedback route](BETA_FEEDBACK.md). Explain
four total voices, supported Companion platforms and actual MIDI capabilities.

## Installer and support boundaries

The Hub's [knowledge base](https://thefirmwarehub.com/kb/) describes package
checks and browser installation; that is not FMER runtime or migration testing.
Validate the exact FMER port identity, updater, origin/destination layouts,
save/backup guidance and return path on designated hardware before advertising
one-click installation there. A directory listing is a separate acceptance item.
Ask how automatic release pickup treats prereleases, draft releases and multiple
assets. Keep GitHub as the canonical source/download and issue tracker.

Send links rather than unsolicited attachments or private diagnostics. Keep
creator attribution and upstream credits. Record contacted date, response,
listing URL and any integration tests here after the owner authorizes outreach.
All contacts are currently **researched / not contacted by the agent**.

## Suggested introduction

FMER is a free, open-source firmware for the M-VAVE FM-1, combining six-operator
FM and virtual analog synthesis with polyphonic playing, arpeggiation,
four-track sequencing and song arrangements. Its offline Windows Companion
handles supported installation, backups and patch/project management.

Lead with a completed musical example; link the detailed feature list. Ask one
question per community post and route reproducible bugs to the optional issue
forms. Code-contributor status remains reserved under CONTRIBUTING.md; beta
feedback does not require a pull request.
